# Research: Susegad UI on Shopify

*6 October 2026. A research run on Shopify as a distribution channel for Susegad UI's components, scenes and future templates, with a resin-jewellery store in Goa as the first case. Primary sources are shopify.dev, the Shopify developer changelog, help.shopify.com, Shopify's own GitHub repos and shopify.com/news; everything else is marked as secondary. Claims we could not confirm from a primary source carry the tag **(unverified)**. Bundle sizes in section 8 were measured today in this repo with esbuild 0.28.2 (minified ESM, gzip -9 and brotli).*

## Summary

Shopify's Online Store is now built the way Susegad already builds: server-rendered HTML enhanced by light-DOM custom elements, with no framework (Dawn defines a dozen light-DOM custom elements; Horizon has a `Component` base class with refs and declarative `on:` events, and loads ES modules through an import map). Pieces can enter a store three ways: as files copied into a theme (sections, theme blocks, snippets and assets), as an app whose theme app extension offers up to 30 app blocks, or as a whole theme. The real constraints are these. A theme's `assets/` folder is flat, and modules that import each other by relative path lose Shopify's `?v=` cache-busting. App blocks get a *suggested* 10 KB of compressed JS per file and an *enforced* 100 KB of Liquid in total, and cannot use colour scheme settings. An app must not lower the storefront Lighthouse score by more than 10 points (home 17%, product 40%, collection 43%). The Theme Store wants original code (not Dawn or Horizon), more than twenty required features, a demo store per preset and exclusivity, for 85% of $140 to $500 sales. Checkout belongs to Shopify, and in India it runs through third-party gateways (Razorpay, PayU, Cashfree) plus COD and India-only one-click checkout apps. Measured today, a Susegad component bundles to 4 to 8 KB gzip and a scene to 20 to 27 KB gzip; split into chunks, that is a shared scene runtime of about 11 KB plus 9 to 13 KB per scene. So components fit the app block guidance and scenes fit only if they load lazily behind a poster. **Recommendation:** pilot route (a), a `--target shopify` mode in our CLI that writes hashed flat ES modules plus Liquid sections and theme blocks into a theme. Run it on the resin store with four pieces: a "poured on, cures in" lead-time note driven by metafields, the Abri scene as a poster-first section break, a testimonial quote and a custom-order `reach` block. Build route (b), a theme app extension, from the same output once the pilot's numbers hold. Treat a full theme (c) as a later product, not a channel test.

## 1. Themes today

### Online Store 2.0, JSON templates, sections and blocks

- **Folders.** A theme has `assets`, `blocks`, `config`, `layout`, `locales`, `sections`, `snippets`, `templates` (with `templates/customers` and `templates/metaobject`). "Subdirectories, other than the ones listed, aren't supported." Only `layout/theme.liquid` is mandatory. Assets can be `.js.liquid` or `.css.liquid` to read `settings` and Liquid filters. [Theme architecture]
- **JSON templates** "act only as a wrapper for sections". Sections are reusable modules that merchants add, remove and reorder; section groups do the same for header and footer areas. [Theme architecture]
- **Limits** [Theme limits]: 25 sections per JSON template; 50 blocks per section; 1,250 blocks per template or section group; **8 levels** of theme block nesting (excluding the section); 300 theme block files; 20 section groups of 25 sections each; 1,000 JSON templates. File limits: JSON template and section group 512 KB; `settings_schema.json` 512 KB; `settings_data.json` 1.5 MB; other Liquid files 256 KB each; a single `liquid` setting 50 KB; theme zip 50 MB; 100,000 files. Section and block schema `name` at most 25 characters.
- **Theme blocks** live in `blocks/` at the theme root, are reusable across sections, nest inside each other and render with `{% content_for 'blocks' %}`. A section opts in with `"blocks": [{ "type": "@theme" }]` and may add `{ "type": "@app" }` for app blocks; a section either defines local blocks or accepts theme blocks, not both. Presets are required for a block to appear in the editor. **Static blocks** render in fixed positions with `{% content_for "block", type: "...", id: "..." %}` and cannot be moved or deleted by merchants. [Theme blocks; Static blocks]
- **Horizon** (Summer '25 Edition, May 2025) is the first public theme built fully on theme blocks, with group blocks and up to eight levels of nesting, and AI block generation in the editor. Horizon is now the default theme for new stores (secondary sources: anatta.io, codrops). Its repo says it is "web-native", server-rendered, and not accepting contributions. The latest release notes in the repo are for **4.2.0** (RTL support and fixes); the colour palette changelog cites **Horizon 4.0.0** as the reference implementation of `color_palette`. [Horizon repo; Color palettes changelog]
- **Winter '26 Edition** (17 December 2025): over 250 Horizon improvements, "block generation for all themes" from the Theme Store, editing products, collections, markets and metafields without leaving the theme editor, 2,048 variants per product. [shopify.com/editions/winter2026]
- **Summer '26 Edition** (17 June 2026): native A/B testing of themes and checkout, theme-controlled `/agents.md`, `/llms.txt` and `/llms-full.txt` (secondary sources only: fudge.ai, novadata.io, li.solutions) **(unverified on shopify.dev)**; colour palettes for themes (primary, below).
- **Liquid July '26 developer preview** (21 July 2026): a `{% block %}` tag that renders a theme block straight from a template with inputs and body content, and a `{% partial %}` tag that "defines a named region of server-rendered HTML that JavaScript can refresh without reloading the full page". Page structure can live in a Liquid template instead of JSON. Preview only, in development stores. [Changelog: Liquid block and partial tags]
- **Canvas** (1 October 2026): a new design surface where Sidekick, Shopify's AI agent, "works directly on the theme's files" on a simplified theme architecture. At launch it is desktop-only, and "third-party theme support, app blocks and extensions, markets, translations, rollouts, and theme updates are all not part of the initial launch"; Shopify says it plans to support them. It does not replace the theme editor yet. [Shopify news: Introducing Canvas; TechCrunch] This matters to us: Sidekick and Canvas compete with section libraries, and our prompt-and-map files are exactly the kind of material an agent that edits theme files could use once third-party themes and app blocks are supported.

### How Dawn and Horizon use custom elements

- **Dawn** (`assets/global.js`) defines `quantity-input`, `menu-drawer`, `header-drawer`, `modal-dialog`, `bulk-modal`, `modal-opener`, `deferred-media`, `slider-component`, `slideshow-component`, `variant-selects`, `product-recommendations` and `bulk-add`, all in light DOM, with no references to `Shopify.designMode` or `shopify:section:*` events. The elements' own lifecycle is enough. Its principles: HTML rendered by Liquid, web-native, JavaScript only as needed. [Dawn repo; Dawn global.js]
- **Horizon** loads ES modules through an import map in `snippets/scripts.liquid`, with aliases such as `@theme/component`, `@theme/dialog`, `@theme/product-form`, `@theme/variant-picker`, `@theme/morph` and `@theme/events`. It adds `<link rel="modulepreload" fetchpriority="low">` for common utilities and loads feature scripts only when a setting turns the feature on. Its `Component` base class (`assets/component.js`) extends `HTMLElement` through `DeclarativeShadowElement`, works in light or shadow DOM, collects child elements by `ref` attributes (with `[]` for arrays and `requiredRefs`), wires `on:click/method` style declarative events, uses a MutationObserver to keep refs fresh, and offers an `updatedCallback` for Section Rendering API re-renders. It also has no `shopify:section:load` handling: re-rendered sections simply connect new elements. `layout/theme.liquid` renders `color-palette` and `theme-styles-variables` snippets for CSS custom properties, and has a view-transitions opt-in. [Horizon scripts.liquid; component.js; theme.liquid]

This is our architecture. Susegad's `SgElement` (`packages/core/component.js`) is light-DOM, enhances a native child, mounts in `connectedCallback`, tears down a microtask after `disconnectedCallback` if the element did not come back, and supports `connectedMoveCallback`. `<sg-scene>` (`packages/core/scene-element.js`) uses a shadow root with a slot for the reading layer, which is fine for slotted Liquid content.

### Settings schema types

Basic: `checkbox`, `number`, `radio`, `range` (numeric `min`, `max`, `default`; optional `step`, `unit`), `select` (2 to 5 options render as a segmented control, 6 or more as a dropdown), `text`, `textarea`. Specialised: `article`, `article_list`, `blog`, `collection`, `collection_list`, `page`, `product`, `product_list`, `color`, `color_background`, `color_palette`, `color_scheme`, `color_scheme_group`, `font_picker`, `html`, `image_picker`, `inline_richtext`, `richtext`, `text_alignment`, `link_list`, `liquid`, `metaobject`, `metaobject_list`, `url`, `video`, `video_url`. List pickers default to a limit of 50. [Input settings]

- **`color_palette`** (17 June 2026): one per theme, only in `settings_schema.json`, 2 to 20 named colours, hex without alpha. Sections and blocks can default a colour setting to a palette entry (`settings.colors.<key>`), and merchants can override per section or block. Colour schemes keep working, palettes are not required for the Theme Store, but "future development is focusing on palettes". [Color palettes changelog; Input settings]
- **App blocks cannot use colour scheme settings**: "Color scheme settings aren't supported in app blocks." Whether an app block can read the theme's global `settings.colors` is not documented **(unverified)**. [Input settings]
- **Dynamic sources** let a merchant connect a setting to a metafield or metaobject in the editor. At most 50 dynamic sources in one setting and 100 per JSON template, static section or section group. [Dynamic sources]

### Theme editor events, and what a web component must do

The editor fires `shopify:inspector:activate` and `deactivate`, `shopify:section:load`, `unload`, `select`, `deselect` and `reorder` (detail `{ sectionId }`, plus `load` on select), and `shopify:block:select` and `deselect` (detail `{ blockId, sectionId, load }`). `Shopify.designMode` is `true` in the editor. When a setting changes, a section's "HTML is dynamically added, removed, or re-rendered directly onto the existing DOM, without reloading the entire page. However, any associated JavaScript that runs when the page loads won't run again." Scripts must re-initialise on `section:load` and "clean up any event listeners, variables, etc." on `section:unload`. [Integrate sections and blocks with the theme editor]

What this means for a Susegad element:

1. **Custom elements already survive the editor.** New HTML upgrades and runs `connectedCallback`; removed HTML runs `disconnectedCallback`. Dawn and Horizon rely on exactly this. Nothing may initialise from `DOMContentLoaded` alone.
2. **Teardown must be complete.** A scene must stop its `requestAnimationFrame` loop, disconnect its observers, and release its WebGL context (`WEBGL_lose_context`) on disconnect, or each settings tweak leaks a running loop. `<sg-scene>` has a `#teardown()` that destroys the renderer and governor; whether every renderer releases its GL context should be checked in the pilot **(unverified for every scene)**.
3. **Respect `shopify:block:select`.** When a merchant selects a block holding a scene, the scene should pause on its still frame (or play, if they ask), and slides or tabs should reveal the selected block. A small editor shim, loaded only when `Shopify.designMode` is true, can do this.
4. **Module scripts run once.** A `<script type="module">` inside re-rendered section HTML does not run again, and a module is evaluated once per page anyway. So loading must live in the element (`connectedCallback` triggers the import), not in a script beside it.
5. **The Section Rendering API returns sections, not blocks**, and cannot set setting values. [Section Rendering API]

### Liquid's limits

The documented limits are structural (above): Liquid files at most 256 KB each, a `liquid` setting at most 50 KB, a theme app extension's Liquid at most 100 KB in total. Since 13 January 2026 Shopify enforces **stricter Liquid parsing**: existing themes were rewritten in the background, and pushes and saves with syntax errors are blocked. [Community changelog: Stricter Liquid parsing] Liquid cannot create metafields. Render-time limits (loop limits, render timeouts) are not on the limits page we read **(unverified)**. Shopify caches rendered pages, so anything "honest by the clock" (days until ready, open now) should be computed in the browser, with Liquid printing an absolute date as the no-JS fallback **(caching behaviour of `'now'` unverified on shopify.dev)**.

### CSP and script loading norms

- Shopify's guidance: `defer` non-critical scripts, `async` only for independent third parties, `import()` inside event listeners for code needed only on interaction, Liquid and HTML for initial content, `image_url` and `image_tag` for images, eager loading for anything in the first viewport (especially the LCP image), and at most one or two `preload` hints. [Performance best practices]
- **Theme Check `AssetSizeJavaScript`** flags any single JS file, local or remote, over **10,000 bytes compressed** by default. For theme app extensions the check is off by default with severity "suggestion". [AssetSizeJavaScript]
- **CSP.** On standard plans merchants cannot set HTTP response headers; a `<meta>` CSP in `theme.liquid` works but cannot carry `frame-ancestors`, `report-uri`, `report-to` or `sandbox`. Shopify injects its own scripts into `<head>` through `content_for_header`, and most apps inject inline scripts, so a strict CSP breaks most apps (secondary: Pea Soup Digital, March 2026). Practical rule: our code must need no `eval`, no `new Function`, no inline event handlers and no third-party hosts, so it works under whatever CSP a merchant chooses. Shopify's own documentation on storefront CSP defaults was not found **(unverified)**.

### asset_url, ES modules and import maps

- `{{ 'file.js' | asset_url }}` returns a CDN URL with a `?v=` version parameter. A relative `import './other.js'` from that module resolves to the same flat folder but **without** the version parameter. A developer reported in March 2025 that files imported this way served stale content after a deploy, with no staff answer. [Community: Module scripts for theme extensions] The vite-plugin-shopify-import-maps README describes the same gap and fixes it with an import map whose entries come from `asset_url`. [vite-plugin-shopify-import-maps]
- **Import maps** used to be unusable on Shopify because a page could have only one, and no module could load before it. Shopify pushed a **merge algorithm for multiple import maps** into the HTML spec, Chromium and WebKit; it shipped in **Chrome 133 and Safari 18.4** (article dated 28 May 2025). Shopify injects the `es-module-shims` polyfill where needed. Firefox support was not stated **(unverified)**. [Shopify Engineering: Resilient import maps]
- Horizon itself uses an import map. So two working patterns exist: (1) bare specifiers resolved by an import map built from `asset_url` (Horizon's way), or (2) **content-hashed file names** with plain relative imports, which need no map and cannot go stale, because a changed file gets a new name. We recommend (2) for its simplicity and browser reach, with (1) as an option.

## 2. Theme app extensions

### App blocks and app embeds

- **App blocks** are Liquid files that merchants place inside sections (or theme blocks) that accept `@app`; Dawn and Horizon support them, and the Theme Store requires them in the main product and featured product sections. **App embed blocks** have `target` `head`, `compliance_head` or `body`, are switched on and off in the editor's App embeds panel, and suit floating or invisible pieces (a chat button, analytics, a global loader). [About theme app extensions; Configuration; Theme Store requirements]
- Schema: `name` (keep under 25 characters), `target`, optional `javascript`, `stylesheet`, `enabled_on`, `disabled_on`, `class` (always includes `shopify-block`), `tag`, `settings`, `default`, and `available_if` (an app-data metafield, for example `{{ app.metafields.conditional.block1 }}`, that gates the block). [Configuration]
- **Asset injection.** The `javascript` attribute adds a `<script async>` in `<head>` when the block is on the page, **once per page** however many blocks reference it; stylesheets behave the same. It is a classic script; for modules a block writes its own `<script type="module" src="{{ 'x.js' | asset_url }}">` or, better, lets an element import on demand. [Configuration]
- **Cannot:** edit theme code, render on checkout, or read `content_for_header`, `content_for_index` or `content_for_layout`. They work only with Online Store 2.0 themes. [Configuration; About theme app extensions]
- Since Canvas launched (1 October 2026) without app block support, app blocks do not yet appear in Canvas-built stores. [TechCrunch]

### Limits

| Limit | Value | Status |
|---|---|---|
| App blocks per extension | 30 (was 10, then 25; raised to 30 on **3 February 2026**) | enforced |
| Liquid across all files | 100 KB | enforced (custom-distribution apps may request an exception) |
| Total extension size | 10 MB | enforced |
| Locale files | 100 files, 15 KB each | enforced |
| JavaScript per file, compressed | 10 KB | suggested, not enforced |
| CSS, compressed | 100 KB | suggested |

[Configuration; Changelog: app block limit to 30; Distribution]

An extension's `assets/` is also a flat folder in practice; the docs call it a subdirectory of the extension and do not mention nesting **(nesting unverified, assume flat)**.

### How merchants add them

Install the app, open the theme editor, add an app block to a section like any block, or toggle an app embed. Apps should give deep links and setup instructions. On uninstall, "blocks that are associated with the apps are automatically and entirely removed". [App requirements; Built for Shopify requirements]

### Review, performance and Built for Shopify

- **App Store requirements:** use theme app extensions and avoid manual code changes; work in the theme editor; "Your app shouldn't reduce Lighthouse performance scores by more than 10 points", measured as a weighted average of home (17%), product (40%) and collection (43%) before and after install; keep branding to a 24 by 24 pixel attribution unless customers interact with it. [App requirements checklist; Storefront performance]
- **Built for Shopify:** at least 50 net installs from paid shops, at least 5 reviews, a minimum recent rating; admin Web Vitals at the 75th percentile (LCP at most 2.5 s, CLS at most 0.1, INP at most 200 ms, from at least 100 calls over 28 days); the same 10-point storefront Lighthouse rule; theme app extensions for anything in the online store. [Built for Shopify requirements]
- **Review time:** the posted SLA was 8 to 10 days, but developers on the community forum in 2026 report 3 to 4 weeks for a first review, blamed on a surge of AI-made submissions; resubmissions take 5 to 10 business days to start, then 2 to 3 per round (community reports, not an official figure). [Community forum threads]
- **Distribution and money:** a **custom-distribution** app installs on one store (or one Plus organisation) with **no review**, can use theme app extensions, but cannot charge through Shopify's billing. Admin-created custom apps can no longer be made and could not use extensions anyway. Public apps keep 100% of the first $1,000,000 of gross app revenue earned from 1 January 2025 and 85% above it; the Partner registration fee is $19 once. [Distribution; App revenue share]

## 3. The Theme Store

- **Performance and accessibility:** a minimum average Lighthouse performance score of **60** and accessibility of **90**, across product, collection and home, on desktop and mobile, with real images and content. [Theme Store requirements; Testing for performance]
- **Code:** native CSS only (no Sass); no minified `.css` or `.js` "with the exception of ES6 and third-party libraries"; scripts hosted on Shopify except approved libraries; nothing that "interferes with, or augments, any native Shopify feature". No JavaScript size cap appears in the current text. [Requirements]
- **Required features (abridged):** sections everywhere; a Custom Liquid section; app blocks in main product and featured product; faceted filtering; accelerated checkout buttons; gift card template; pickup availability; product recommendations (related and complementary); rich media (3D, video); predictive search; newsletter; Shop Pay Installments; unit pricing; selling plans in the cart; Follow on Shop; multi-level menus; country and language selectors; variant images; social metadata; blocks for all or most elements of the product page's main section; rich product snippets for SEO. Since **30 July 2026**, the **`<shopify-account>` component** must be in the header on desktop and mobile for new themes and updates; legacy customer accounts are deprecated. [Requirements; Changelog: shopify-account requirement]
- **Originality:** "Themes on the Theme Store must be fundamentally different from other themes", not reproducible by settings, and "New theme submissions built on or derived from Dawn or Horizon are not eligible". The Skeleton theme (`shopify theme init`) is the approved starting codebase; otherwise the code must be original. A cohesive palette of at least four colours, a merchant-first editor. [Requirements; Create a theme]
- **Presets and demo stores:** one preset takes the theme's name; at least one demo store per preset, matching its tagged industry (up to 2 of 20) and catalog size; real copy, test payments only, no apps except free reviews or translation. The `/listings` folder became required on **15 May 2025**, with a Theme Store redesign in July 2025. [Requirements; Changelog: Theme Store requirements May 2025]
- **Exclusivity and support:** "Themes listed on the Shopify Theme Store can only be distributed through the Shopify Theme Store." Merchant support within two business days. [Requirements]
- **Money:** 15% revenue share on gross theme sales (so 85% to the developer), plus a 2.9% processing fee and tax charged separately since 1 August 2021, no submission fee. [Theme Store revenue share] Prices of paid themes run roughly **$140 to $500** one-time per store (secondary sources only: fuelthemes.net, qualimero, charleagency) **(unverified)**.
- **Timeline:** the submit page says only that details take up to 24 hours to show in the Partner Dashboard, and warns that resubmitting without fixing the reasons for rejection can lead to a suspension. No review duration is published. [Submit a theme]
- **Selling outside the store:** allowed for a theme that is not listed there (a ZIP the merchant uploads, our own site, a marketplace), but then there is no Theme Store discovery and updates are manual. A listed theme cannot also be sold elsewhere. [Requirements]

## 4. Headless

- **Storefront Web Components** load from `https://cdn.shopify.com/storefront/web-components.js`. `<shopify-store store-domain="..." [public-access-token] [country] [language]>` sets credentials; `<shopify-context type="product" handle="...">` scopes data and holds a `<template>`; `<shopify-data>`, `<shopify-money>`, `<shopify-media>`, `<shopify-variant-selector>`, `<shopify-list-context>` and `<shopify-cart>` (a native `<dialog>` with `showModal()` and `addLine()`, styled with CSS parts and slots) do the rest. `buyNow()` sends the shopper to Shopify-hosted checkout. A token is needed only for inventory, metafields and metaobjects. Shopify calls them unversioned APIs that "might change at any time". [Storefront Web Components; Getting started; shopify-store; Common patterns; search result for API versioning]
- **Hydrogen** is React on React Router 7 (2026.4.0, 17 April 2026, made the Storefront API proxy mandatory and deprecated `@shopify/remix-oxygen`); a June 2026 developer preview moves Hydrogen's commerce logic into a framework-agnostic core (secondary: weaverse.io) **(unverified on shopify.dev)**. **Oxygen** hosting is included on Starter, Basic, Grow, Advanced and Plus plans (not "Agentic" plans), with 10 MB workers, 400 ms startup, 30 s CPU and 128 MB per request. [Hydrogen fundamentals]
- **Fit for us.** Headless loses the theme editor, which is where boutique makers actually work, and client-rendered product content is weaker for SEO (the Storefront Web Components docs say nothing on SEO). Hydrogen is React, against our framework-agnostic core. Storefront Web Components are useful for one case: a maker who already has a non-Shopify site (an Astro site from our studio, a Folio document, a printed QR menu page) and wants a "buy" button or a small cart on it. Our light-DOM components can wrap a `<shopify-context>` without conflict. Rank: a side door, not the main route.

## 5. Cart and product APIs a component would use

- **AJAX Cart API** (`/{locale}/cart/add.js`, `cart.js`, `update.js`, `change.js`, `clear.js`; always build URLs from `window.Shopify.routes.root`). Line item `properties` record per-item choices; keys starting with `_` are private (shown in admin, hidden only if the theme hides them). `selling_plan` attaches a plan. **Bundled section rendering** returns up to **five** re-rendered sections with the cart response, so a cart drawer and a header count update in one round trip. [Cart API]
- **Section Rendering API**: `?section_id=` or `?sections=a,b` (up to five), in the Liquid context of the URL requested, with existing settings only; no block rendering. [Section Rendering API] The Liquid July '26 `{% partial %}` preview is aimed at the same job for named regions.
- **Product and variant data:** Liquid objects on the server; `/products/<handle>.js` gives product JSON to scripts (long-standing endpoint, not re-checked today **(unverified)**); themes typically print a `<script type="application/json">` blob for the variant picker. Variants per product rose to 2,048 (Winter '26).
- **Metafields and metaobjects:** read as `{{ product.metafields.custom.cure_days.value }}`; types include date, date_time, integer, decimal, boolean, rich text, references and JSON; bracket notation for keys that clash with filter names; cannot be created in Liquid. Merchants can bind a section or block setting to a metafield through dynamic sources. Metaobjects with storefront access can be dynamic sources anywhere and have their own templates (`templates/metaobject`). [Metafield object; Dynamic sources; Theme architecture] For our lead-time idea: product (or variant) metafields `custom.poured_on` (date) and `custom.cure_days` (integer), plus a shop-level default, feed a block that prints "Poured on 2 October. Ready to ship from 5 October." in Liquid and refines it in the browser.
- **Selling plans:** `product.selling_plan_groups`, `selected_selling_plan`, and a `selling_plan` input in the product form; plans are created by apps, and merchants must qualify for subscriptions. Pre-order and try-before-you-buy are separate "deferred purchase options" and need an app with extension access. [Subscriptions in themes; search result on admin-created apps] A cure-time note does not need any of this: it is information, not a purchase option.

## 6. India specifics

- **Plans and fees:** Basic ₹1,994 a month (₹1,499 billed yearly), Grow ₹7,447 (₹5,599), Advanced ₹30,164 (₹22,680), Plus from ₹1,75,000. Because **Shopify Payments is not available in India**, Shopify adds a third-party transaction fee of 2% (Basic), 1% (Grow), 0.6% (Advanced) or 0.2% (Plus) on top of the gateway's own fee. Manual methods, including **COD** (a reserved name in Shopify), carry no third-party fee. [shopify.com/in/pricing; Manual payments; secondary sources on Shopify Payments availability]
- **Gateways and UPI:** Razorpay, PayU, Cashfree, CCAvenue and Pine Labs install as payments apps and offer UPI (including intent flows on phones), cards, net banking, wallets and EMI inside Shopify checkout; Payfuture added a UPI and net banking integration in July 2026 (secondary: The Paypers, Crowdfund Insider). [Razorpay Shopify page; secondary comparisons]
- **One-click checkout layers:** Razorpay Magic Checkout, GoKwik (KwikCheckout), Shiprocket Checkout and Shopflo replace or front Shopify's checkout with saved addresses from a shared shopper network, COD risk scoring and prepaid incentives. A known pain: they do not support some bundle apps (community thread). [Razorpay Magic; community thread; secondary comparisons] This is the main reason "checkout is Shopify's" is only half true in India: the checkout a shopper sees may be GoKwik's. Our pieces stop at the cart.
- **COD:** secondary industry sources put COD at about 45% of Indian D2C orders in 2026 and around 60% of all e-commerce orders, with COD return-to-origin rates of roughly 24 to 35% against about 3% for prepaid (ProfitBox360, Pointnxt, Angadi Labs) **(secondary, varying methods)**.
- **WhatsApp:** Interakt, Wati (₹1,999 to ₹13,499 a month), AiSensy and Gallabox are the common Meta-API apps for Indian Shopify stores: abandoned-cart nudges, COD confirmation (vendors claim 30 to 40% less RTO), order and shipping updates, broadcasts. [Interakt app listing; secondary roundups]
- **Number formatting:** Shopify's money formats (`{{amount}}`, `{{amount_no_decimals}}` and the separator variants) do not do lakh grouping (₹1,00,000) **(secondary, consistent with Shopify's help page on currency formatting)**. For a ₹1,200 to ₹4,200 pair of earrings it never matters; for furniture or gold it does, and our `en-IN` helper could format client-side.
- **What a boutique maker's store looks like.** One public Goan resin-jewellery store, looked at today: Shopify, INR with a country selector, a WELCOME10 code, free shipping over ₹2,400, collection heroes, product grid with bestseller badges, a "kind words" testimonial block, a founder's note and a newsletter. Missing: any dispatch or lead-time line, any COD or prepaid message, a WhatsApp link (custom orders go through Instagram DMs), visible reviews. The Goa business audit in this repo (`docs/reports/2026-10-06-goa-business-audit.md`) independently lists the same gaps for artisans: variants as swatches, a shipping note, reviews, a cart that ends in WhatsApp. Typical gaps across Indian maker stores (our reading, not a survey): honest made-to-order timelines, size and care guides, real photos at true scale, trust signals that are not fake urgency, and pages that are slow on mid-range Android phones over 4G.

The pattern: builders win on drag-and-drop and lose on speed (18 to 35 Lighthouse points in heavy cases) and lock-in ("the page HTML is locked inside the app"). Section stores win on ownership. Susegad's pitch fits the second camp and goes further: no runtime dependency, the code is yours, a poster first, a still under reduced motion, accessibility as a blocker, and a prompt that teaches.

One gap found: `<sg-scene>` has no poster. It draws its own still from the model, but that still needs the JavaScript. On Shopify, the poster must be a real `<img>` that Liquid renders, so it can be the LCP element and the no-JS result.

### Shared building blocks for all three routes

1. **Flattener.** Map the folder tree to flat names and rewrite imports. `packages/core/component.js` becomes `sg-core-component.<hash8>.js`; `packages/components/menu/skins/warm.js` becomes `sg-menu-skin-warm.<hash8>.js`. Every relative import (`'../../core/component.js'`, and the literal skin loaders `() => import('./skins/warm.js')`) is rewritten to `./sg-...<hash>.js`. The hash is the first 8 hex digits of the file's sha256 *after* its own imports are rewritten, computed leaves first over the dependency graph (the CLI already has `graph.js`, `imports.js` and `hash.js`). Content-hashed names make the stale-module problem impossible and need no import map. Two modes: **readable** (one file per source file, unminified, our comments kept: what "copy-in, you own it" promises, and ES6 is exempt from the Theme Store's no-minified rule) and **packed** (esbuild-style chunks per piece: fewer requests, used for the app). Template-built paths (``import(`./x/${name}.js`)``) cannot be rewritten by regex; the registry build should reject them for Shopify targets.
2. **Poster-first loader** (`sg-lazy`, under 1 KB). Liquid renders:
   ```liquid
   <sg-lazy src="{{ 'sg-scene-abri.<hash>.js' | asset_url }}" register="{{ block.settings.register }}">
     {{ block.settings.poster | image_url: width: 1600 | image_tag: loading: poster_loading, widths: '480,800,1200,1600', sizes: '100vw', alt: block.settings.poster_alt }}
     <sg-scene name="abri" register="{{ block.settings.register }}" seed="{{ block.settings.seed }}" hidden></sg-scene>
   </sg-lazy>
   ```
   The element imports `src` only when it is near the viewport (IntersectionObserver with a 200px margin), after `load`, and when none of these hold: `prefers-reduced-motion`, Save-Data, register `quiet`, or a very low-end device (`deviceMemory` at most 2, or the governor's own lite tier). Then it unhides the scene and fades the poster out once the first frame is drawn. Otherwise the poster stays: that is the still. The poster gets `loading="eager"` and `fetchpriority="high"` only when the merchant marks the section as the first on the page (a checkbox), because Liquid cannot know it; `poster_loading` in the sketch is a variable assigned from that checkbox (`'eager'` or `'lazy'`). A sketch, not tested Liquid.
3. **Tokens snippet.** `snippets/sg-tokens.liquid` writes our CSS custom properties from settings: register on `:root` (`data-register`), and a palette mapped either to one of our named palettes (a `select`) or to the theme's `color_palette` entries (`settings.colors.<key>`, so the merchant's brand colours flow into our OKLCH tokens). Our type tier is left alone; Shopify's `font_picker` can feed `--sg-font-body` and `--sg-font-display`.
4. **Settings mapping.**

   | Susegad | Shopify setting | Notes |
   |---|---|---|
   | register | `select`: quiet, warm, playful (segmented control), plus "Follow the page" | Section or block level; global default in `settings_schema.json` (route a and c) or an app embed (route b). |
   | palette | `select` of named palettes, or `color` settings defaulting to `settings.colors.*` | App blocks cannot use colour schemes. |
   | seed | `range` 1 to 99 | Plus a "Shuffle" note in `info`. |
   | numeric params | `range` | `min`, `max`, `step` must be numbers. |
   | enum params | `select` | |
   | slotted text | `inline_richtext` or `richtext` | Rendered as the light-DOM child the scene slots. |
   | poster | `image_picker` with our JPG as the default asset | `image_tag` gives responsive `srcset` for free. |
   | motion | checkbox "Play when visible" | Off means poster only. |
   | data | dynamic sources: product metafields, metaobjects | For example `cure_days`. |

5. **Editor shim** (loaded only when `Shopify.designMode`): on `shopify:block:select`, pause scenes inside the block on their still and scroll them into view; on `shopify:section:unload`, nothing extra is needed beyond our `disconnectedCallback`, but the shim can assert in development that no loops are left running.
6. **Liquid emitter.** From each `registry.json` (title, description, registers, params, `useFor`) generate a `sections/sg-<name>.liquid` and a `blocks/sg-<name>.liquid` with schema, presets, `enabled_on` hints from `useFor` (a `hero` scene on index and collection templates; a `loader` nowhere), and locale strings. The prompt file goes into the theme's repo as `sg-<name>.prompt.md` beside the theme (not in the theme, which accepts no extra folders), so Sidekick or any agent working on the theme files can read it.

### Route (a): copy-in Liquid via the CLI (`--target shopify`)

`npx @susegad/cli add scene-abri quote reach --target shopify --dir ./my-theme` writes `assets/sg-*.js` and `assets/sg-*.css` (flat, hashed), `sections/sg-*.liquid`, `blocks/sg-*.liquid`, `snippets/sg-lazy.liquid`, `snippets/sg-tokens.liquid`, and `locales/en.default.schema.json` additions (merged, not overwritten), and records everything in the lockfile so `diff` and later updates work. The developer pushes with `shopify theme push` or GitHub sync.

- **Bundling:** readable mode by default, no build step at the merchant's end; the CLI stays dependency-free because flattening is string rewriting plus hashing.
- **Scene budget:** scene runtime plus one scene is about 20 KB gzip, loaded only on visibility after load, behind a poster. Lighthouse's lab run sees only the poster.
- **Editor-safety:** inherent, as above; tested by adding, duplicating, reordering, changing every setting and removing each section ten times with no console errors and no leftover animation frames.
- **Effort:** the flattener and Liquid emitter are a contained CLI feature (one emitter, templates per kind); each piece then needs a schema review. Sections plus theme blocks cover both Dawn-style and Horizon-style themes.
- **Risks:** merchants without a developer cannot run a CLI (so this route serves studios and developers, not makers directly); theme updates keep new files when they do not conflict, but edits in templates and `settings_data.json` do not carry over [Updating themes]; our sections must not clash with the theme's CSS (prefix everything `sg-`, use `@layer`); readable mode means many small requests (mitigate with `modulepreload` for a piece's closure, which the CLI knows from the graph); the relative-import behaviour on theme CDN URLs should be confirmed on a development store first.

### Route (b): a theme app extension app

An app ("Susegad plates", working title) whose extension holds up to 30 app blocks (for example 6 scenes as section breaks and heroes, a lead-time note, quote, reach, tile-band, gallery, stamp) and one app embed for the global register, palette and the `sg-lazy` loader (via `javascript`, async and deduplicated).

- **Bundling:** packed mode: per-piece entries plus shared hashed chunks in the extension's `assets/`, each under 10 KB compressed except the scene runtime (about 11 KB, so split engine and element to get under). Extension asset URLs carry a version in their path **(unverified)**, which would make relative imports safe even without hashing; hashing anyway costs nothing.
- **Scene budget:** as route (a). The weighted Lighthouse test (17/40/43) mostly hits product and collection pages, where we would place nothing heavy.
- **Settings:** per block, as in the table; no colour schemes in app blocks, so palettes are our named ones or plain `color` settings.
- **Liquid budget:** 100 KB across 30 blocks is about 3 KB each; schemas with presets and locales fit.
- **Editor-safety:** the same, plus app blocks must look right inside any merchant's theme, so our CSS needs container queries and must inherit the theme's text colour and font.
- **Effort:** route (a)'s emitter plus an app shell (Shopify CLI app, OAuth, hosting) and an App Store listing; an app needs a backend even if it does nothing else **(minimum hosting needs unverified)**. Custom distribution for the pilot needs no review.
- **Risks:** the code no longer belongs to the merchant (uninstall removes the blocks, which is clean but is the lock-in we criticise in page builders; mitigation: an "eject to theme" button that runs route (a)); review queues of weeks; the 30-block cap; pricing (one-time per block like Section Store, or a small monthly fee) only through public distribution; no Canvas support for app blocks yet.

### Route (c): a full theme

A Susegad theme for makers, built from the Skeleton theme, with our components as its native sections and blocks, registers and palettes as presets (quiet, warm and playful presets would satisfy "one preset per demo store" and give three listings).

- **Bundling:** readable mode throughout; an import map is optional.
- **Scene budget:** the Theme Store's bar is an average Lighthouse score of 60, easy for a server-rendered theme with poster-first scenes; our own bar should be 90 or more.
- **Effort:** the largest by far. Every required feature (faceted search, predictive search, accelerated checkout buttons, pickup availability, unit pricing, selling plans, gift cards, `<shopify-account>`, rich media, recommendations, multi-level menus, localisation) has to be built and kept current as requirements change (four changes in the last 18 months alone), plus a demo store per preset, merchant support within two business days, and an original design that is "fundamentally different" from Dawn and Horizon.
- **Risks:** exclusivity if listed; review timelines unpublished; Sidekick and Canvas may make bespoke themes cheap for merchants; revenue only on one-time sales of $140 to $500. The upside: the best showcase of the library, and full control of performance.

### Route (d), for completeness: Storefront Web Components on our own sites

For a maker with an Astro site from our studio: our pieces plus `<shopify-store>`, `<shopify-context>` and `<shopify-cart>`, checkout on Shopify. Little effort, but unversioned APIs and no theme editor. Worth one recipe later, not a channel.

## Recommendation

**Ranking.**

1. **Route (a), copy-in Liquid via the CLI.** It matches our distribution model (code copied, owned, changeable), needs no review or app hosting, works in Dawn-style and Horizon-style themes, and builds the flattener, Liquid emitter, poster loader and settings mapping that every other route reuses. Its audience is developers and studios (including ours) setting up stores for makers.
2. **Route (b), a theme app extension**, built from route (a)'s output once the pilot proves the budgets in real stores. This is how a maker without a developer gets our pieces, and the App Store is where discovery happens. Start with custom distribution, then list publicly with one-time pricing per piece, Section Store style, and an "eject to theme" escape hatch so it stays honest about ownership.
3. **Route (c), a full theme**, only after (a) and (b) show which pieces makers actually keep. It is a product with a support burden, not a way to test the channel.
4. **Route (d), headless**, as a recipe for our studio's own sites, not a channel.

**Pilot for a resin-jewellery store.** Do it on a development store first, with a copy of the store's live theme (with the owner's friend's permission), then on the live theme behind a draft.

| Piece | Where | Why | Status |
|---|---|---|---|
| **Lead-time note** ("Poured on 2 October. Cures for 3 days. Ships from 5 October.") | Product page block, also a small line on product cards | Resin pieces are made and cured; a made-to-order maker's most-asked question; the store observed shows no lead time at all | **New piece**, harvested from this store (charter rule 6). Metafields `custom.poured_on` (date) and `custom.cure_days` (integer) per product or variant, shop default via a metaobject. Liquid prints the absolute dates (no-JS truth); a tiny element turns them into "ready Thursday" in IST in the browser, honest by the clock as in `event-list` and `now-note`. Says "Made to order" when stock is zero, never a fake countdown. |
| **Scene Abri** as a section break or collection hero | Home page and one collection, never product pages | Marbled drops of pigment pushed into rings are the look of a resin pour; quiet shows the print as a still | Exists (40 KB budget, about 20 KB brotli bundled). Needs the poster loader and a palette set from the store's own pigments (our palette-from-photo tool). |
| **quote** for the existing "kind words" | Home page | Replaces a generic testimonial block with one that names the source | Exists. |
| **reach** for custom orders | Product page and footer | Custom orders now go through Instagram DMs; reach gives a real WhatsApp link, email, and copy-the-number, with no third-party script | Exists. |
| **tile-band** (optional) | Divider on an azulejo-themed collection | Only if the maker has such a collection and wants it; regional motif, credit in docs | Exists. |

**What to build first.**

1. The flattener and `--target shopify` emitter in the CLI, proven on `quote` (smallest, no scene): section plus theme block, settings, editor test in Dawn and Horizon development stores, and a check that relative imports of hashed assets load from the theme CDN.
2. The lead-time note, as a normal Susegad component with its pure core, three registers, prompt and tests, plus its Liquid block and metafield definitions.
3. `sg-lazy` and the poster pipeline (poster JPG into `assets/` as the `image_picker` default, `image_tag` srcset), then Abri on it.
4. `reach`, and the register and palette settings in `settings_schema.json`.

**What to measure.**

- **Lighthouse, Shopify's way:** mobile and desktop, home 17%, product 40%, collection 43%, median of five runs, before and after. Our bar is a drop of at most 3 points (Shopify's app rule is 10), accessibility at 90 or more with axe showing no violations in all three registers.
- **Field data:** the store's Web Performance dashboard (LCP, INP, CLS at p75 by page type and device) for 28 days before and after, so we see mid-range Android phones on Indian networks, not our laptops.
- **Bytes:** JS per page type (brotli) from DevTools; scene JS must be zero on product pages and zero on any page until the scene is visible.
- **Editor-safety:** the ten-times add, duplicate, reorder, change, remove script with no console errors and no running frames afterwards.
- **For the maker:** how many lead-time questions arrive by DM in the weeks before and after (she counts; we add no tracking, per the charter), WhatsApp custom-order enquiries, and the add-to-cart rate on product pages from Shopify's own analytics. Note COD and prepaid shares too, but the pilot should not touch checkout, so they are context, not a result.
- **Our own cost:** time for the friend (or a developer) to add, configure and remove each piece without our help.

**Biggest constraints, in one place.** Flat `assets/` and unversioned relative imports (solved by hashed names); 10 KB compressed JS per app block file (suggested) and 100 KB Liquid per extension (enforced); the 10-point Lighthouse rule for apps; no colour schemes in app blocks; Theme Store originality, required features, exclusivity and the new `<shopify-account>` requirement; checkout untouchable, and in India often replaced by one-click checkout apps; `<sg-scene>` needs a real poster `<img>` before any of this works; Canvas and Sidekick do not support third-party themes or app blocks yet, and AI block generation now competes directly with section libraries.
